# 视频上传支持可行性评估

## Goal

评估把 Picsur 从纯图床扩展为支持视频上传的可行性与代价，回答「难度大不大、需要改哪些地方、有什么坑」，产出可直接决策的结论与最小改造清单。本轮只做评估，不写实现。

## Requirements

- R1 以仓库真实实现为准：后端（存储/校验/接口/转换/限额）、前端（上传/图库/详情/分享/嵌入/i18n）、部署（Dockerfile/compose/反代/资源限制）逐项核对，结论附文件路径与行号。
- R2 区分两档范围并分别评估：A. 存原片直出（不转码）；B. 追加转码 + 封面海报 + Range 流式播放。
- R3 覆盖关键风险：上传大小/时长限制与 fastify bodyLimit、超时、磁盘与带宽增长、Range/Streaming 响应、mime 与魔数校验、安全与滥用（无转码任意文件、SSRF/恶意媒体、合规）、Docker 镜像体积（ffmpeg/sharp 并存）、备份与清理。
- R4 给出结论：值不值得做、推荐 MVP 范围、依赖与工作量量级（不是精确工期）、以及可直接开工的任务拆分草案。
- R5 本轮只读：不写代码、不改配置、不装依赖、不重启服务；调研笔记只写入本任务 `research/` 目录。

## Acceptance Criteria

- [ ] 一句话结论 + 判断依据（现在哪些约束决定了视频「能发」的门槛）。
- [ ] 改造点清单，按后端 / 前端 / 部署 / 数据与运维分组，逐项附证据（文件:行号）。
- [ ] A / B 两档方案对比（改动范围、风险、外部依赖、验证方式）。
- [ ] 推荐路线与 MVP 任务拆分（可直接转 implement 的粒度）。
- [ ] 所有关键数字可复核（限额、镜像体积、依赖版本等），并标注不确定项。

## 评估结论（2026-10-25）

- 三份并行调研已完成：`research/backend.md`（后端/契约）、`research/frontend.md`（Angular 侧）、`research/infra-security.md`（部署/限额/安全/上游）。本项目录与完整报告见本轮对话。
- 一句话：**前端不是门槛；门槛在存储与传输模型**——图片二进制存 Postgres `bytea`（无文件系统）、`/i/*` 无 Range/ETag、镜像无 ffmpeg、无队列。「图床能顺手收小视频 + 直链」是小—中工作量；「拖动播放/手机 Safari 正常」需要存储层重构 + Range/206；「转码 + 海报」是独立子系统。
- 推荐路线：先拍板档位再立项（A0 最小闭环 / A+ 正常播放 / B 转码海报），任务拆分草案在对话报告与两份调研文件 §6；本轮未改任何业务代码。
- 上游先例：本仓自维护版本线 0.10.6；上游 Picsur 已 NOT MAINTAINED，公开 issue/PR/README 检索不到视频支持（URL 见 `research/infra-security.md` §6）。
