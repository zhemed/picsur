# 构建并发布新镜像替换热部署

## Goal

用户要求「发版」：把当前已验证的视频功能（上传、11 容器、Range 206、页面播放）提交入库，构建正式镜像并替换本机 8080 的热部署容器，数据与配置保留，可回滚。

## 现状

- 8080 运行的是热部署产物，镜像仍是旧的 ghcr.io/zhemed/picsur:allinone 0.10.7；容器重建会退回旧版。
- 工作区有多个已归档任务的未提交改动：视频上传、Range 与播放、容器扩展、规范文档与任务记录。
- 仓库发布流程为 support/release-local.sh：要求干净工作树、已推送提交、版本 tag 一致，构建普通镜像与 allinone 镜像，推送 ghcr 并打 git tag；需要 ghcr 登录与网络。

## Requirements

- R1 提交全部代码与任务记录，提交信息带任务锚点；推送 origin。
- R2 按仓库发布脚本构建新镜像；版本号策略按仓库惯例处理，不能造成 :latest 回退。
- R3 用新镜像重建 8080 容器，保持 /data 挂载、端口 8080、restart always、env 与 docker.sock 挂载不变。
- R4 切换前导出旧容器配置与旧镜像信息，失败可恢复旧容器。
- R5 验证：健康、登录、图片数据完好、视频回归、mov 与 mkv 上传、mp4 与 webm 播放、Range 206、清理测试数据。
- R6 若 ghcr 推送因未登录或网络不可用失败，必须区分「本地镜像已构建并部署成功」与「远端推送失败」，给出补齐步骤。

## Acceptance Criteria

- [ ] 代码与任务记录已提交并推送。
- [ ] 新镜像构建成功，记录镜像 ID 与标签。
- [ ] 8080 容器由新镜像运行，healthy，/api/info 200。
- [ ] 管理员登录与既有图片数据正常。
- [ ] 视频回归与浏览器抽查通过。
- [ ] 旧容器配置已备份，回滚步骤明确。
- [ ] 远端推送结果明确记录。

## Risks

- 构建耗时与网络依赖：需要拉基础镜像与推送 ghcr。
- 版本号与已有 tag 冲突。
- 容器重建期间服务短暂中断；/data 为 bind 挂载，数据不受容器重建影响。
