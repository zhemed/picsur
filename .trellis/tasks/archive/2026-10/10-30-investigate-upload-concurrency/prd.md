# 调查上传图片逻辑是否单核串行

## Goal

用户（项目所有者）怀疑 Picsur 的图片上传逻辑实际是「单核串行」运行。本任务只读调查上传链路各环节的并发模型，给出有证据的判定：哪些环节确实串行、哪些环节其实并发、真正的瓶颈在哪里；并列出可优化的候选方向。本任务不实施任何代码改动。

## Background

- 上传链路横跨：Angular 前端上传控件 → 后端 HTTP 接口与请求体解析 → 图片解码/编码处理 → 存储写入 → 数据库写入 → Node 运行时与容器资源。
- 用户体感：批量上传时耗时近似线性叠加，感觉像只用了一个核。需要区分两种可能：前端一次只发一个请求造成「串行体感」，以及后端图片处理 CPU 密集阻塞事件循环造成「单核事实」。
- 相关既有结论：`10-25-video-support-eval` 已查明二进制存 Postgres `bytea`、无文件系统、无队列；本任务聚焦并发模型而非存储模型。

## Requirements

- R1 覆盖调查以下环节，逐环节给出「串行 / 并发」判定：前端上传行为、HTTP 入口与限流、图片处理库与线程模型、存储写入、数据库写入、Node 运行时与部署资源。
- R2 每条结论必须有可复核证据：源码 `文件:行号`，或只读命令的原文输出；读不到即写「未读到」，禁止臆造。
- R3 给出总体判定：上传链路是否「单核串行」，并区分「前端串行体感」与「后端单核事实」两类原因各自是否成立。
- R4 输出瓶颈点清单，按影响排序，每条标注「确认」或「推测」，推测项写清验证方法。
- R5 全程只读：不改源码、不改配置、不装依赖、不构建、不重启服务、不动容器状态；调研笔记只写入本任务 `research/` 目录。
- R6 优化实施不在本任务范围，只给候选方向与建议的后续任务拆分。

## Notes

- 判定「单核」的关键在图片处理环节：若为纯 JS 解码/编码且跑在事件循环上，则无论容器给多少核都只用到一个核；若为原生库线程池，则实际并发度由线程池与 CPU 配额共同决定。
- 前端并发与后端并发都可能造成体感差异，结论中需分别说明。

## 调查结论（2026-10-30）

**判定：部分成立。** 前端串行体感成立；后端「单核」只在单张图处理这个粒度上成立；整条链路不是全局单核串行。

统一口径分三层，三份报告与规格文档已按此对齐：

1. 前端：上传并发上限固定为 1，是批量慢的直接来源。`upload.component.html:3` 无 `multiple`，
   `processing.component.ts:35` 只上传 `imageFiles[0]`，批量 `UploadImages` 被注释且目标端点不存在；
   多选、拖多张、粘贴多张时其余文件被静默丢弃。
2. 后端受理与并行：单 Node 进程并发受理请求，上传链路无全局锁；每次转换 `fork` 一个独立子进程，
   多请求同时到达时可由操作系统调度到多核。主进程的同步 JS 段（SVG 净化、类型判定与 `isSvg` 全文扫描、
   WebP 头解析）会阻塞事件循环，SVG 上传最明显。
3. 单张图内部：默认主格式 QOI 的编解码是 `qoi-img` 原生插件同步调用，worker 内单线程、不经 libvips
   线程池；非 QOI 编解码才走 libvips 线程池。所以单张图上传处理基本只吃一个核。

已确认瓶颈，按影响排序摘要，完整清单见
`.trellis/spec/picsur-backend/backend/upload-concurrency.md` §3.5：

1. 每次转换新 fork 一个子进程，无常驻池，固定进程启动开销。
2. 单实例单进程部署，主进程同步段无法分摊。
3. 主进程同步纯 JS CPU 段阻塞事件循环。
4. 主进程 sharp metadata 预检受 libuv 默认 4 线程池限制。
5. 整文件读入内存，单文件上限 128MB。
6. 图片字节存 Postgres bytea，请求内串行 2 到 3 次写，pg 默认池 10。
7. 上传后浏览还会再触发一次转码，非 SVG 图生命周期至少两次 fork 级转换。
8. 上传限流每 IP 每分钟 20 次，进程内计数，超限拒绝不排队。
