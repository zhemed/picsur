# admin 用户名无法修改

（本目录是 10-17 轮补全的任务记录；同轮调查结论与用户决定见下，原 10-16 目录版本已归档。）

## 成因

0.10.6 修复"密码被权限 403 连带拒掉"时，Lead 的指令写过头了 ✗：让前端在 locked-perms 账号上**同时剔除 `permissions` 与 `username`** ✗ → 用户名编辑被静默丢弃 ✓。

## 待实测

后端是否允许改用户名（`UserUpdateRequest = EntityIDObjectSchema.merge(SimpleUserSchema.partial())` ✓ 结构上允许 ✓）：用 admin 的 token 发 `{id, username:"admin2"}` 看状态码；**改完立刻改回** ✓。

## 修法（取决于实测）

- 若**允许** ✓ → 前端只剔除 `permissions`，保留 `username` ✓；
- 若**不允许** ✗ → 前端把用户名字段**明确置灰并说明原因** ✗（不许静默忽略 ✗）。

## 验收

- [ ] UI 上能改用户名（或明确不可改 + 原因）✓；
- [ ] 改密码仍可 ✓、改权限仍 403 ✓（不回归 0.10.6 的修复 ✓）；
- [ ] 回归脚本补一条：admin 改用户名 → 期望结果 ✓；
- [ ] 三包构建 + 两个回归全绿 ✓。

## 调查结论（2026-10-17，Lead 实测）

1. **现状：任何用户都无法改名** ✗ —— `POST /api/user/update` 服务实现里**没有写 `username` 的语句**（DTO 允许 ✓），改名会返回 **201 但静默不生效** ✓（实测：发 `admin2` → 响应与库里都仍是 `admin` ✓）。
2. **admin 额外有"按名字"的硬约束** ✗：
   - `ImmutableUsersList.includes(user.username)` → 保护其不被删除/不被降权；
   - `if (ImmutableUsersList.includes(user.username)) return SuperUserPermissions;` → **超权限靠名字匹配**。
   改名 = 丢"内置超管"身份 ✓ → 不再受保护（可被降权/删除 → 自锁 ✓）+ 将来新增权限不会自动授予 ✗。
3. **要安全支持 admin 改名**需一次小重构 ✗：把内置超管识别从**按名字**改为**按 id/专门标记**（加列或固定 id 判据 + 数据迁移 + 权限判据改造 + 回归）✓。
